# Stream 6 — registration + parents: design calls

**Date:** 2026-11-14 · **Status:** built, awaiting Adebayo's review · **Builds on:** `2026-11-03-assessment-first-admission-design.md` (S3 assessment fields), `2026-11-03-scheduling-design.md` (S4 preference chips), `docs/sop/parents-module.md`.

**Goal.** The public `/enroll` wizard and the admin walk-in capture the parent/guardian, and create or link a `Parent` record, with many children per parent. Level, format, location, schedule and course were already captured by Streams 2-4; this stream adds who is registering and who is responsible. **No new migration**: the existing `Parent`/`Student` schema suffices.

**Not changed (by instruction):** fee once per student (D13), the Paystack webhook, the tuition ledger, the outbox design, the status machine.

## The shape of the problem
`Student.email` is unique and identifies a person. A second child registered with the parent's email would be silently upserted onto the *first* child's `Student` row (the old `update: {}` branch), merging two children. So "multiple children per parent" first needs a way to give a child an identity without an email of their own.

## Calls

| # | Call | Why / rejected alternative |
|---|---|---|
| **S6-1** | **Matching a parent**, strongest identity first: (1) the guardian's email, exact, lower-cased (`Parent.email` is unique); (2) **only when no email was given (admin walk-in)**: the phone, and only if **exactly one** parent has that number (compared by last 10 digits, so `0903…`, `+234 903…`, `234903…` are one number). Never on name. Several phone matches = ambiguous = nobody linked. A phone that matches while a *different* email was given does **not** link: a different email is treated as a different person, a new parent is created, and the admin sees a "possible duplicate: same phone" notice on the parent. | A public form cannot verify anyone, so only the exact key `Parent.email` is trusted there; the public path never links by phone. Rejected: fuzzy name matching, auto-merge of parents. |
| **S6-2** | **Minors vs adults.** The wizard's first question is "Myself (18+) / My child or someone under 18" (`registeringFor`). The server decides: `registeringFor='child'`, **or** a date of birth under 18 (even if the form says "myself"), makes the registrant a minor. A minor needs a guardian **name and email** (public) or name + email *or phone* (admin). An adult needs their own email; a guardian is optional ("someone else handles lessons and payments") but a guardian email needs a name. A guardian that is the student's own mailbox is ignored. If the form omits `registeringFor` (old clients, API) the date of birth alone decides. | The date of birth is optional on the form, so a declared choice is needed; the server does not take an adult's word against its own record. The existing `guardianName/Phone/Email` fields on `Student` are reused (no duplicate fields). |
| **S6-3** | **A child with no email of their own** is keyed on a `+tag` of the guardian's mailbox: `mum+ada-okafor@gmail.com`. Same guardian + same child name = the same student (a second course for Ada finds Ada); different first names = distinct students; same first name with contradicting birth dates = distinct (`…-20120101`). A child email that is just the guardian's mailbox, or that already belongs to someone with a different first name (a parent typing their own registered email), is ignored in favour of the alias. | `Student.email` must stay unique and required (making it nullable touches every consumer and is not additive). Mail to the alias reaches the guardian; the S7 recipient builder now treats `mum+ada@x` and `mum@x` as one mailbox so the guardian is not emailed twice. **Caveat:** providers that do not support `+` addressing (notably Yahoo) will not deliver to the alias; the guardian's own address is stored on the student and parent. |
| **S6-4** | **Second child from the public form, no enumeration.** The form always sends the same fields; the server matches the parent by exact guardian email behind the scenes and links. The response is the same JSON shape whether the parent was new, existing or not linked (checked on the real route: a new guardian, an existing guardian and a never-seen guardian give one shape; the fee-covered path was not exercised with a guardian). Throttles: per IP, per applicant email, and **per guardian email** (8 per 10 min). Beyond 12 children on one parent the public form still takes the application but no longer links (audited `parent.registration_link_refused`). | Adding a "do you already have an account?" step would add a leak. The pre-existing residual leak (a fee-covered student is redirected to the site, a new one to Paystack) is unchanged. |
| **S6-5** | **Never overwrite, never trust a stranger.** An existing parent's data is never changed from a public form. The admin walk-in may fill a **blank** phone only (audited). A public submission attaches a guardian only to a student **created by that request**, or to one already stored with that exact guardian email: typing an existing student's email plus your own address as "guardian" links nothing. Linking happens after the application is real (payment initialised / covered application created), is best-effort, and never changes the response. | The parent record is contact data only (no portal), but a link would otherwise let a stranger attach themselves to someone else's student. Rejected: emailed confirmation links (heavy; listed as a follow-up for Adebayo). |
| **S6-6** | **Consent.** Parent has no consent column (no migration). A parent's marketing eligibility stays derived from their children's enrollments (`consentToEmails`), as S7 built it, with one tightening: **only enrollments past `pending`/`cancelled` count** (`parentConsentFlags`, used by the announcement audience and the birthday cron). A public application that never reached the paid stage therefore cannot opt a real parent into marketing; a parent with no linked child has no consent and is never marketed to (and is not in any audience, as before). The wizard's consent box reads "As the parent or guardian…" for a child application. Transactional mail is unaffected. | Same consent derivation as S7, just not spoofable through the unauthenticated form. **Not changed:** the *student* side of S7 (a pending application's consent flag counts for that student's own marketing): a follow-up. |
| **S6-7** | **Admin.** `/admin/parents` shows each parent's children with their live applications (course, location, status), a derived marketing badge (Consented / No consent / No child linked), a possible-duplicate notice (same phone) on the edit dialog, and a per-parent **Register another child** action that opens the walk-in modal preset to that parent. The walk-in modal gains Adult/Child, a parent search (pick an existing parent: their record is not changed), guardian fields, optional student email for children, and a guardian-consent label. The child picker now lists students with any live application (was: enrolled only) and shows their stage. | Closes the "child-picker lists only enrolled students" follow-up. |
| **S6-8** | **Audit.** `parent.registration_create` / `parent.registration_link` (public rows have `adminId` null; walk-in rows carry the admin) with source, student, enrollment, matched-by, filled-phone and same-phone parent ids; `enrollment.admin_create` metadata gains `minor`, `parentId`, `parentResolvedByPhone`. | |
| **S6-9** | **Payer.** For a minor the Paystack customer email and `ApplicationPayment.billingEmail` are the guardian's, not the alias. | Paystack's own receipt goes to the person paying. |

## Out of scope / follow-ups
Email-verified linking from the public form; making student-side consent equally spoof-proof; a phone-only guardian on the *public* form; an admin "merge parents" tool; unsubscribing a parent.
